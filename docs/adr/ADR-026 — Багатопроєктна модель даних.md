ADR-025 — Багатопроєктна модель даних
Статус

Accepted

Контекст

Після переходу ERP КУБ до підтримки декількох проєктів виникла необхідність забезпечити можливість існування однакових кодів документів та елементів у різних проєктах без зміни бізнес-логіки модулів BOM, планування виробництва та обліку матеріалів.

Рішення

1. Таблиця 19_ProjectDocuments

Первинний ключ:

ID

Альтернативний (бізнес-) ключ:

(ProjectID, Code)

де

ProjectID — проєкт;
Code — код документа (наприклад, КР.7).

Унікальність забезпечується саме цією парою.

2. Таблиця 00_Elements

Первинний ключ:

ID

Кожен елемент містить

ProjectDocumentID

що визначає документ, якому належить елемент.

Після введення ProjectDocumentID поле

Code

більше не вважається глобально унікальним.

Бізнес-ключ елемента:

(ProjectDocumentID, Code) 3. Використання ключів

Для всіх внутрішніх зв'язків ERP використовується тільки

ID

або

ProjectDocumentID

Коди використовуються лише як бізнес-ідентифікатори та для роботи користувача.

4. Пошук документів

Допускаються два види пошуку.

За технічним ключем

ID
↓
ProjectID
Code
Name

та за бізнес-ключем

(ProjectID, Code)
↓
ID 5. Наслідки

Модулі

BOM
Production
Placement
Materials
Planning

не потребують зміни своєї бізнес-логіки.

Усі вони працюють через ElementID або ProjectDocumentID, не використовуючи ProjectID або HouseID.

6. Роль таблиць
   18_Projects

Описує проєкти та використовується для:

групування документів;
вибору проєкту;
звітності.
19_ProjectDocuments

Є центральною таблицею багатопроєктності.

Саме вона пов'язує:

Project
│
▼
ProjectDocument
│
▼
00_Elements
20_Houses

Описує будинки та використовується для:

формування виробничих комплектів;
вибору будинку;
друкованих форм;
звітності.

Вона не бере участі у зв'язуванні виробничих даних.

Висновок

На мою думку, це одне з найсильніших архітектурних рішень у проєкті. Воно дозволяє додати багатопроєктність, не змінюючи ядро ERP.
