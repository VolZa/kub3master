# ProductionPlanning — виробничий контекст і вимоги

Дата: 2026-10-14. Статус: вимоги для майбутнього проєктування; для архітектурної перевірки. Не Accepted ADR/DDS і не затверджений контракт даних.

## 1. Призначення та місце документа

Вибрано `docs/domain/PRODUCTION-PLANNING-CONTEXT.md`: docs/README.md відносить виробничу предметну модель до docs/domain; docs/requirements у репозиторії відсутній. Дублікат у docs/requirements не створюється. Розташування документа не надає його концептам статусу прийнятої моделі.

## 2. Погоджені виробничі факти

Джерело F01–F14 — погоджені користувачем факти. Окрема технологічна верифікація в межах цього документа не виконувалася.

| ID | Погоджений факт | Межа твердження |
|---|---|---|
| F01 | У цеху шість плитних форм: дві 3×3 м і чотири 3×4 м | Це склад ресурсів, не гарантований випуск за зміну |
| F02 | Бетонування плит зазвичай послідовне, форма за формою | «Зазвичай» не означає обов'язкової заборони іншого порядку |
| F03 | За зміну можуть виготовити менше шести плит через неготовність армування, нестачу працівників, ремонт обладнання тощо | Шість форм не дорівнює шести виконаним плитам |
| F04 | Теоретично одна плитна форма може вміщувати два невеликі вироби | Допустимість потребує окремої технологічної перевірки; це не approved capability |
| F05 | Ті самі форми раніше використовували для тротуарної плитки та стільниць сторонніх замовлень | Історичне використання не підтверджує поточний дозвіл/готовність |
| F06 | Є форма для двох колон за цикл; колони входять до проєкту КУБ | Підтверджено місткість, не обов'язкове завантаження обох місць у кожному циклі |
| F07 | Є оснащення для 10 фундаментних блоків товщиною 400 мм, 6 — 300 мм, 1 — 500 мм | Точні фізичні форми, конструкція та незалежність місць ще невідомі; не «17 форм» |
| F08 | Є форма для однієї балки під сходовий марш; зараз не використовується | Наявність не доводить готовність до запуску |
| F09 | Форми блоків можуть використовуватися для технологічних залишків бетонної суміші після плит і колон | Не означає гарантований залишок або обов'язкове його використання |
| F10 | Формування допоміжного блока може тривати кілька змін | Завершення зміни не дорівнює завершенню виробу чи звільненню форми |
| F11 | Для додаткового армування таких блоків використовують обрізки арматури з однієї ємності без сортування й кількісного обліку | Достовірні кількість, характеристики і партійне походження не встановлені |
| F12 | Такі блоки зазвичай використовують для допоміжних потреб; армування між шарами не доводить конструктивної придатності | Не можна автоматично прирівняти до конструктивного проєктного виробу |
| F13 | Начальник цеху має власний Google-акаунт і повинен редагувати позмінні завдання, включно з поточною зміною | Наявність акаунта не підтверджує нинішні ERP/Sheet permissions |
| F14 | Коригування плану не стирає виконане бетонування; невиконаний план не означає брак виробу | План, виробничий факт та оцінка якості — різні поняття |

## 3. Концептуальне розмежування

Назви нижче — вимоги до розмежування відповідальностей для майбутнього проєктування. Поля, таблиці, IDs, statuses, lifecycle, repositories та технічні зв'язки ще не затверджено.

| Поняття | На яке питання відповідає | Що не слід з ним ототожнювати |
|---|---|---|
| FormResource — ресурс форми | Яке фізичне оснащення існує та зайняте/доступне у певний час? | Номер рядка плану, виріб, його BOM або кількість місць |
| FormCapability — можливість форми | Які вироби, кількості та поєднання технологічно дозволені за визначених умов? | Лише геометрична місткість чи історичне використання |
| FormLoad — завантаження форми | Яке конкретне використання ресурсу заплановано або відбувається протягом певного періоду/циклу? | Одна зміна або вже завершений факт виготовлення |
| FormLoadItem — позиція завантаження | Який виріб/кількість займає частину конкретного завантаження? | Окремий фізичний ресурс; автоматично незалежний цикл |
| ShiftPlan — позмінний план | Що призначено виконати у цю зміну з поточними пріоритетами й обмеженнями? | Фактичне бетонування, споживання чи підтвердження якості |
| Фактична виробнича подія | Що реально сталося з конкретним завантаженням/виробом, коли та ким зафіксовано? | Намір у плані або автоматичний результат закриття зміни |

ProductionRequirement у прийнятій термінології — що потрібно виготовити; ShiftTask — конкретне завдання на зміну. Майбутні FormLoadItem і ShiftTask мають різні ролі: один описує склад завантаження, інший — позмінне призначення роботи. Точний mapping до поточного ShiftPlanItem відкритий.

Manufacturing — первинне введення виробничого журналу; ProductionLog — нормалізований виробничий запис. Майбутні події бетонування/продовження/завершення не оголошуються новою заміною цих accepted понять. Потрібно окремо визначити, які події є проміжними та що саме підтверджує виготовлення у чинному контурі.

## 4. Вимоги до планування та виконання

- PP-01. Кількість плитних FormResource не задає автоматично планову чи фактичну продуктивність. План має враховувати готовність армування, персонал, стан обладнання та доступність форм; деталізація цих обмежень потребує проєктування.
- PP-02. Планування має підтримувати звичну послідовність бетонування й оперативну зміну порядку. Ні точні тривалості, ні паралельність, ні гарантована кількість циклів за зміну не задані.
- PP-03. Одна форма повинна бути відокремлена від одного виробу: дві колони за цикл мають бути виражені складом завантаження. Два невеликі вироби на плитній формі не дозволяти лише за ознакою «поміщаються»; потрібна затверджена технологічна capability.
- PP-04. Ураховувати спільне використання фізичного оснащення для різних виробів, щоб план не призначав один ресурс несумісним завантаженням одночасно. Історичні сторонні вироби не створюють автоматичного дозволу на їх виробництво.
- PP-05. Облік оснащення блоків не повинен перетворювати 10/6/1 місць у вигадані незалежні фізичні форми. Інвентаризація ресурсу і capability передує остаточній ресурсній моделі.
- PP-06. Невикористовувана форма балки відображається як наявний ресурс без припущення про її виробничу готовність чи автоматичне включення в план.
- PP-07. FormLoad допоміжного блока має допускати продовження через кілька змін. Поки форма фактично зайнята, перенесення невиконаного завдання не робить її автоматично вільною. Межі циклу та момент звільнення уточнюються.
- PP-08. Зміна, перенесення або видалення планової позиції не видаляє і не переписує факт уже виконаного бетонування. Показувати окремо план, виконане та залишок роботи; часткове виконання не перетворюється на повністю виконане автоматично.
- PP-09. Невиконане/перенесене завдання — відхилення плану, а не дефект якості. Статус браку потребує окремого підтвердження уповноваженої ролі та підстави; роль і процедура ще не визначені.
- PP-10. Оперативні зміни плану потребують простежуваності автора, часу та суті зміни; спосіб revision/history і вирішення одночасних edits визначити при проєктуванні. Ця вимога не вводить нову схему збереження.
- PP-11. Планування використовує виробничий контекст ProjectDocumentID згідно з прийнятими ADR; навігація за проєктом/будинком не повинна втрачати належність виробу до документа. Допоміжні вироби без такого контексту потребують окремого рішення, а не вигаданого ProjectDocumentID.

Збереження факту від планових edits не означає заборону виправлення самого виробничого факту. ADR-046 допускає зміни/скасування факту зі стабільним ID і повторною ідемпотентною синхронізацією. Таке виправлення є окремою дією з відповідними правами, а не побічним ефектом редагування ShiftPlan.

## 5. BOM, матеріали й технологічні залишки

Нормативна потреба, фактичне використання та повторне використання залишків мають бути розрізнені. MaterialRequirement — чиста потреба, розрахована з BOM і виробничого контексту відповідними engines; вона не є фактом споживання/списання або вибором партії. ProductionPlanning не повинен самостійно змінювати BOM чи дублювати material calculation engine.

- MP-01. Залишок бетону після плит/колон — фактична виробнича обставина, а не нова нормативна BOM-потреба і не автоматична величина «розрахований бетон мінус план». Кількість, джерело, придатність та спосіб вимірювання залишку поки не визначено.
- MP-02. Використання залишку для допоміжного блока потребує відокремленого опису походження та фактичного застосування, наскільки дані доступні. Не створювати вигаданий складський баланс, партію або кількісний факт із невідомих даних.
- MP-03. Одна й та сама суміш/арматура не повинна автоматично списуватися повторно як нова закуплена сировина через її повторне використання. Як це узгодити з уже визнаним Consumption/Movement та provenance — відкрите питання Material Flow архітектури, не нова облікова проводка цього документа.
- MP-04. Обрізки в несортованій ємності не мають підтверджених кількостей чи характеристик. Їх не вважати гарантовано доступною нормативною арматурою, не підміняти ними canonical Material/BOM і не виводити точну економію/масу без вимірювань.
- MP-05. Багатозмінне пошарове формування блока не означає автоматичне підтвердження готового виробу після кожного додавання бетону або закриття зміни. Зв'язок проміжних подій із ProductionConfirmed/Manufacturing визначити окремо.
- MP-06. Армування між шарами не підтверджує конструктивної придатності. Допоміжне використання та допуск як конструктивного виробу мають бути відокремлені; критерії й відповідальний за технологічний допуск ще не визначені.

Прийняті DDS залишаються чинними: MaterialLossPolicy відокремлена від чистої потреби, Actual Allocation забезпечує відповідну потребу, Consumption має власну підставу підтвердження. Застосування LossPolicy у Planning вже лишено відкритим у DDS Material Allocation; цей документ не встановлює відсотків втрат і не змінює accepted trigger/ledger/provenance contracts. Несортовані фізичні обрізки не оголошуються автоматично доменним Unresolved Material — mapping потребує окремого рішення.

## 6. Ролі та вимоги до доступу

Погоджена вимога — начальник цеху зі своїм Google-акаунтом може редагувати позмінні завдання, **включно з поточною зміною**. Інші права нижче — пропозиція для архітектурного погодження, не підтверджені поточні permissions.

| Дія | Технолог | Начальник цеху |
|---|---|---|
| Визначати технологічну сумісність і обмеження FormCapability | Запропонована відповідальність; порядок затвердження уточнити | Не отримує це право автоматично через право редагувати план |
| Формувати/узгоджувати технологічну основу завдань | Запропонована роль; межа затвердження відкрита | Може оперативно коригувати позмінні завдання в дозволених технологічних межах |
| Змінювати склад, порядок, перенесення поточних позмінних завдань | Обсяг участі уточнити | Обов'язкове право за F13 |
| Змінювати BOM, технологічні правила чи допуск конструктивної придатності | Окрема політика, не надається цим документом | Право планового edit цього не дозволяє |
| Створювати/виправляти/скасовувати виробничі факти | Окремі права та процедура, ще не визначені | Не випливають автоматично з права редагувати план |

Редагування поточної зміни має зберігати факти і чинні технологічні обмеження. Власний Google-акаунт забезпечує можливість індивідуальної ідентифікації, але не доводить наявність MASTER edit permission. Майбутню авторизацію слід перевіряти на сервері; точні ACL, scopes, Google Groups, executeAs, пряме редагування Sheets і approvals не визначаються тут. Не потрібно надавати начальнику цеху широке редагування MASTER лише для реалізації права на позмінний план.

## 7. Невизначені питання та непідтверджені припущення

| ID | Відкрите питання | Що не можна прийняти без уточнення |
|---|---|---|
| Q01 | Інвентарні IDs, робочі розміри, стан, підготовка/очищення/розпалубка плитних форм | Габарит 3×3/3×4 сам визначає технологічну сумісність |
| Q02 | Які два невеликі вироби сумісні в одному завантаженні; простір, опалубка, армування, технологічні умови | Два вироби дозволені лише тому, що геометрично поміщаються |
| Q03 | Скільки фізичних форм/касет/місць для блоків, які з них незалежні; що означає 10/6/1 в циклі | 17 незалежних форм або гарантований одночасний випуск |
| Q04 | Умови одиночного/парного завантаження колон; актуальний стан форми балки | Будь-який цикл колон завжди дає дві; балка готова до запуску |
| Q05 | Тривалості циклів, зайнятість між змінами, curing/release, персонал і обладнання, можливість паралельної роботи | Шість плит за зміну, один цикл за зміну або обов'язково лише послідовне виконання |
| Q06 | Як фіксують готовність армування, причини відхилень і поточну доступність ресурсу | Наявний точний автоматичний облік цих обмежень |
| Q07 | Вимірювання, походження, час та критерії допустимого використання залишків суміші | Будь-який залишок придатний і має відомий об'єм |
| Q08 | Мінімально можливий облік обрізків: факт використання, маса/характеристики, відповідальний | Точний баланс несортованої ємності чи відома партія |
| Q09 | Проміжні події, завершення/якість багатозмінного блока; відповідальний за допуск | Шар бетону = готовий виріб або армування = конструктивна придатність |
| Q10 | Обліковий provenance повторного використання без подвійного Consumption/Movement | Новий material event/списання без узгодження Accepted DDS |
| Q11 | Планові revisions, approvals, concurrent edits, закриті зміни, права на виправлення факту/брак | Начальник цеху має всі технологічні/облікові права |
| Q12 | Місце допоміжних і сторонніх виробів, product identity, ProjectDocument/House/Placement context | Усі вони входять до КУБ; відсутній контекст можна замінити довільним ID |
| Q13 | Mapping FormLoad/Item/ShiftTask до чинних ShiftPlan/Item та Manufacturing | Нові names автоматично вимагають нових Sheets/міграції |

Припущення для обговорення, не виробничі факти: одне завантаження використовує один ідентифікований ресурс; у завантаження може бути кілька позицій; завантаження може переживати зміну; оперативне редагування плану відбувається в затверджених технологічних межах. Для касетного оснащення та складних багатомісних форм ці припущення потребують перевірки до остаточного дизайну.

## 8. Сценарії для архітектурної перевірки

1. Із шести плитних форм за зміну бетонували чотири: чотири факти збережено; дві невиконані позиції можна перенести, не оголошуючи брак і не записуючи вигадане виготовлення.
2. Начальник цеху зі свого акаунта змінює порядок ще не виконаних завдань поточної зміни: факти попереднього бетонування та технологічні обмеження зберігаються.
3. Пропонують два невеликі вироби на плитній формі: планувальник не вважає пропозицію дозволеною capability без технологічного підтвердження.
4. Колонна форма має дві позиції в одному завантаженні: це не дві фізичні форми; фактичний випуск не створюється тільки з місткості.
5. Допоміжний блок формується кілька змін: завантаження/зайнятість і проміжні факти простежуються між змінами; завершення визначається окремо.
6. У блок додали залишок суміші й несортовані обрізки: не створено вигаданої кількості чи партії, подвійного списання або автоматичного конструктивного допуску.
7. План зменшили після часткового виконання: виконане бетонування залишилося; виправлення помилкового виробничого факту виконується окремим чинним процесом, не плановим edit.

Це критерії для перевірки майбутньої моделі, не результати вже виконаних software/production tests.

## 9. Межі подальшої роботи

Поточна модель має 14_ShiftPlans для планів; SheetConfig вказує 15_ShiftPlanItems для позицій, а поточний ShiftPlanItem.position описано як номер форми 1…6. Згадка `15_ShiftPlan` у постановці не є вказівкою перейменувати, мігрувати чи розширити будь-яку таблицю. Майбутня ресурсна модель потребує окремого погодження mapping, без механічного перенесення position у FormResource.
